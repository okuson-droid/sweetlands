- 作成：Cowork（クロエ）。読みは Claude 4人に分担させた（カードの文面とデータの突き合わせ 3人、エンジンの効果の種類ごとの処理 1人）。
- 動機：AI が測るのはエンジンであり、エンジンがルールを間違えていれば測定は別のゲームのものになる。
- 対象：ブランチ `claude/sim-ai-plan`（コミット e61ba12 時点。`src/game/` と `src/data/` は main の PR #4 時点から変えていない）。
- 材料：`cards_side_by_side.md`（207枚の文面・アイコン・実装の解釈・構造を並べたもの。`sim/src/cardaudit.ts` で生成）、`rules_excerpt.md`（ルール整理テキストの抜粋）、`cards_1-69.md`・`cards_70-138.md`・`cards_139-207.md`（1枚1行の判定）、`engine_semantics.md`（効果の種類ごとの実装の照合、50項目）。

## 1. 結論

- **カードの文面とデータの構造（アイコン表記の解釈）が食い違うものは 207枚中 0枚。** 「2個につき」の each、「1回だけ」、裏向きの指定、建物を置く先の地形、連鎖矢印（コストを1回払って回数分）、都市点・工業点・収入値の条件は、すべて文面どおりに構造化されている。
- **エンジンの効果の処理で、ルールの文面に反すると確定できたものは 0件。** 矢印4種と連鎖、条件の数え方（自身のタグを含む、オールマイティを各列に数える、塗りつぶしの地形は表裏を問わず）、カードのプレイ（ブラウニー割引は自身を含まない、支援タイル13・14の割引）、オートメーション化の条件、産業ボーナスの解決順（印刷 → カード列、入れ子は今の列を終えてから、任意は選ぶ）は一致している。
- 残るのは「ルールの文面だけでは決められない」ものが、データ側 11枚、エンジン側 7件。実物のカードの写真か、持ち主の判断で確定する必要がある（§2・§3）。
- 既存のテスト（`tests/cards.test.ts`・`rules.test.ts`）は変換の網羅と構造までで、**効果の実行時の意味論（支払いの確認・繰り返し・不足時、条件の回数、割引、産業ボーナスの順序）はほぼ検証されていない**（§4）。

## 3. エンジン側で「ルールの文面だけでは決められない」もの（7件。持ち主の判断）

1. **「->」の支払いは任意か強制か。** 実装は必ず「支払う／支払わない」を尋ねる（`engine.ts` 1210-1220）。ルールは「〜を1回支払い」としか書かない。任意でよいなら現状のまま。
2. **払えないとき、収入値が不足するとき。** 実装は効果全体を黙って飛ばす（`canAfford` で false なら return、ログなし。1209）。収入値を0未満にしてよいかも未確定（`addIncome` は0で止める）。
3. **連鎖「コスト -> 条件 =>* 効果」で、条件の回数が0でも支払いを求める。** 確認文が回数を示さないため、払って0回になりうる。影響：ヴィオラ・ヴィヴィッド、ユージーン・ユズ、ジェラート・ジーニアス。
4. **「地図ボード上の建物駒」の数え方。** 実装は時計塔・研究所・ショップを含める（`queries.ts` 180-182）。影響：モニカ・マロンマジック、ウィリアム・ウェファー、カレン・カルアカプ、オートに「N bld =>」を持つ6枚。
5. **カード由来の建物の配置は無料。** `viaAction: false` で既定のコストを払わない（884・916）。便覧冒頭「アクションスペース以外の能力やボーナスによりアクションを実行できる場合、特記がない限りコストは要らない」と整合するが、建物駒の段のコスト（木材・鉄）まで免除かは明文なし。
6. **ブラウニー割引の率（タグ1個につき1ゴールド）と上級スキル10の同割引。** 抜粋では確認できないが、ルール整理テキスト本文 §12.5 の記述（「ブラウニー×-1ゴールド」）と一致している。確認不要と見てよい。
7. **連鎖の右側の効果の順は表記順で固定。オートメーション化したカードは列の末尾に追加。** データ上は実害なし。

## 4. テストで確かめられていない項目（Claude Code への提案）

- `pay` の確認・繰り返し（`->*`）・不足時の挙動。
- `cond` の回数の計算（複数項目は各項の最小値）と each の有無。
- `tagCounts`・`playedCount` の、自身のタグの扱いとオールマイティの扱い。
- ブラウニー割引（自身を含まない、支援タイル13との併用、0で止まる）。
- オートメーション化の提示条件（産業タグなし・列の上限・ダイヤ不足・パス時カード）。
- 産業ボーナスの順序（印刷 → カード列）、入れ子の保留、「任意」の列の選択。
- パス時カードが都市点・工業点の加算の後に解決されること。

いずれも `tests/cards.test.ts` に、構造ではなく実行結果（資源・収入・盤面の差分）を見るテストとして足せる。追補 §4 段階0 の 0-3（カードの効果の検査）と合わせて行うとよい。

## 5. AI の計画への含意

- エンジン側に測定を歪める不一致は見つからなかったので、強化の計画（追補）はエンジンを変えない前提のまま進めてよい。
- §2 の11枚のうち建物の台座（4枚）と産業ボーナスの列（1枚）は合法手の集合を変えるため、P1〜P3 の本測定の前に確定しておくのが望ましい。確定したらデータの修正は `src/data/` の変更になるので、CLAUDE.md の規約（型検査・テスト・ビルド）に従う。
