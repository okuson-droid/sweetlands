## 2. 今回の確定事項（Cowork の判断。理由つき）

- **段階1c は不通過。段階1d を1回だけ挟む。** 1b は「その場の得点」で準備の手が落ち、1c は「準備の手だけ2手先」で得点の手が落ちた。どちらも物差しが2つあることが原因なので、**すべての子を同じ物差し「passScore ＋ Proj_5」で順位付けする**。Proj_5 は第3版の見込みを最終ラウンドだけに使うもので、残りの手番の予算で変換できる勝利点の見積もり。J（手札+2）・H（ディスク+1）・fa2（カード+1）・フリップ（資源+4）が見込みに、得点の手が passScore に入り、物差しが1つになる。
- **これは 1b の判定で予告した「評価関数を順位付けにだけ使う」案である。** 葉は終局の得点のままなので、評価関数の誤りは枝刈りの質にしか効かず、関門の数値には混ざらない。
- **Claude Code の候補1（すべての子に同じ深さの先読み）は採らない。** 計算量が 1c の数倍（v1 の 100倍超）で、「fa2 → カードのプレイ → 得点」のような2手を超える鎖にも届かない。**候補2（主行動の回数の組でフロンティアを分ける）は、1d-1 で人の手がまだ落ちるときの補助として残す。**
- Claude Code の判断4件（J の孫は次の手番の主行動、2手先は主行動の子に限る、前置の両替は計画の列に含める、main の PR #16・#17 を取り込まない）は妥当。
- **打ち切りの規則を置いた（追補 §1 の4）。** 1d で届かなければ強化の実験を止め、マスターに (i) 人の記録を増やして学習へ、(ii) 本測定を相対比較に読み替える、(iii) 続行、のどれかを選んでもらう。Cowork の推奨は (ii)。1b・1c・1d で順位付けの案を3つ試すことになり、これ以上は「v1 の上に重ねる」と同じ形の反復になるため、**1d の次の順位付けの案は Cowork から出さない。**

## 4. 1d の設計の根拠（トレースから）

- `trace_jas.csv` を見ると、人の手番の途中（第22手、パス得点 476）で、計画器の候補の順位の値は 496 に達している。人の局面に乗ってしまえば計画器は得点に変えられる。落ちているのは第1〜11手（パス得点 239〜328）で、人がカードのプレイ（ポリー 18ゴールド、アルディ、ヴィヴィアン 17ゴールド）とフリップで土台を作る段である。これらは「その場の得点」も「2手先の最良」も低く、「残りの手番で変換できる見込み」でしか値がつかない。
- 1c の時間（1局面 150〜480秒）の大半は2手先の孫の解決（エンジンの手）である。Proj はエンジンの手を進めないので、1b の時間（W＝8・E＝8 で 103秒）に戻る見込み。W＝8・E＝8 で測れる。

## 7. 注意事項・落とし穴

- **Proj_5 は順位付けにだけ使う。** `best`（葉の最良）と関門の数値は終局の得点のまま。rank と score を混ぜない（1c と同じ注意）。
- Proj_5 のパラメータは調整しない。1d は順位付けの実験で、調整すると「評価関数の誤りが混ざらない計測」でなくなる。
- peek（`--peek 1`）は診断専用で情報漏れの規約の例外。数値を測定や関門に流用しない（前回と同じ）。
- 第3版の `projection` は、段階1 で「約束の大きい手を取っておいて打たない」問題を起こした（§5E の変更2）。1d では計画器が実際に手を打つので同じ問題は起きないが、Proj_5 が到達点より大きく楽観なら、見込みの表に余計な項がある。報告のみの項目で見張る。
- 前回までの注意（`planR5` の時間と並列化、`stateKey`・`lastFromPlan`、`evalKey`、`refine` の同点処理、コンテナごとの時間）はそのまま有効。
