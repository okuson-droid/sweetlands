## 2. 今回の確定事項（要点。本文は追補 §4 段階1）

## 3. 実装の順番と補足（Claude Code への指示）

1. **評価のキャッシュを先に入れる**（局面のハッシュ → 評価値。決定性を保つ）。0-1 後の 8.6秒を、第3版を足す前に下げておく。ハッシュは `structuredClone` した局面の JSON ではなく、評価に効く項目（資源・収入・タイルの状態・トラック・手札の ID の集合・ディスク・フェイズ・ラウンド・パス済み）だけから作る。
2. **変換の表を `AREAS` から作る関数**を `evaluate.ts` に置く。入力は局面（`prosRate`・`unflipped`・残りの収入フェイズ）、出力は候補の配列 {エリア id、コスト、勝利点、回数の上限}。カードのプレイ候補は `ai.ts` の仮進行の差分から同じ形で作って足す。
3. **Proj_r の貪欲法**。ラウンドを順に回し、使い残しを繰り越す。両替は主行動を使わない換算手段として扱うが、`MAX_CONVERSIONS`＝6 を超えない。
4. `AgentConfig` に `evalVersion: 3` を足す。重みの数で切り替えない。
5. **順位付けにも第3版を使う**（0-1 の topK＝4 の絞り込みはそのまま）。
6. 初期パラメータ（γ 0.8、A_next 7、c_J 3、線形8 は第1版の値）でシード1〜8 を回し、L2 が消えているか・D が使われるかを**先に**確かめる。消えていなければ要件A の実装を疑う（調整に進まない）。
7. CEM で共通の重みと追加調整（第5版 §6.4）。
8. 関門の計測（シード1〜100、引き継ぎプレイ、`check` の `cards`・決定性・情報漏れ）。

迷いそうな箇所：
- 裏返し1回の見込みの「収入+1 の価値」は、表の中で最も高い「資源1単位あたりの勝利点」× 残りの収入フェイズとする。再帰にしない。
- 第5ラウンドでパス済み（`passed`）の局面は Proj＝0。`finished` の局面は確定得点のみ（従来どおり）。
- 繁栄トラックのレートは `prosRate`（今の区間）を使う。区間をまたぐ効果（レートが上がる）は見込みに入れない。入れたくなっても、まず関門を測ってからにする。
- 「5ゴールド1点」は `scoreTotal` の換算に合わせる。これが変換の表の最低保証になる。
